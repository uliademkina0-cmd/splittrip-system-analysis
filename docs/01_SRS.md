# Спецификация требований к программному обеспечению (SRS)
**Проект:** SplitTrip — Сервис учета и разделения групповых расходов  
**Стандарт:** ISO/IEC/IEEE 29148  
**Версия документа:** 1.1  

---

## 1. Введение

### 1.1. Назначение
Документ определяет функциональные (FR) и нефункциональные (NFR) требования к системе **SplitTrip**, предназначенной для учета совместных расходов в поездках, автоматического распознавания товарных позиций из бумажных чеков (OCR), мультивалютной конвертации и расчета оптимального графа взаиморасчетов между участниками.

### 1.2. Границы системы
* **Входит в объем (In-Scope):** управление поездками и составом участников, загрузка чеков и интеграция с внешним OCR-провайдером, ручное и автоматическое распределение позиций, конвертация валют по курсам ЦБ РФ / ЕЦБ, расчет итоговых переводов, гостевой доступ по ссылке.
* **Не входит в объем (Out-of-Scope):** проведение реальных денежных переводов (эквайринг, СБП), хранение банковских карт пользователей, автоматическая выгрузка транзакций из банковских приложений по Open Banking API.

---

## 2. Функциональные требования (FR)

### FR-1. Управление поездкой и жизненным циклом участников
* **FR-1.1.** Система должна позволять создавать пространство поездки (`Trip`) с указанием названия, дат начала и окончания, а также **Базовой валюты расчета** (`base_currency`, ISO 4217, например `RUB` или `EUR`).
* **FR-1.2.** Смена базовой валюты поездки запрещена после добавления хотя бы одной траты.
* **FR-1.3.** Для каждого участника в рамках поездки фиксируется период активности: `joined_at` (дата присоединения) и `left_at` (дата выбытия, опционально).
* **FR-1.4.** При создании новой траты с выбором опции «Разделить на всех» система автоматически включает в расчет только тех участников, для которых дата чека (`tx_date`) попадает в период их активности: `joined_at <= tx_date <= left_at` (или `left_at` не задана).

### FR-2. Загрузка и распознавание чеков (OCR)
* **FR-2.1.** Система должна принимать файлы изображений (`JPEG`, `PNG`, `HEIC`) и документы (`PDF`) размером не более `10 МБ`.
* **FR-2.2.** Взаимодействие с внешним OCR-провайдером должно осуществляться асинхронно через брокер сообщений с постановкой задачи в очередь и возвратом статуса пользователю (`UPLOADED` -> `PROCESSING` -> `PARSED` / `FAILED`).
* **FR-2.3.** Система должна извлекать из ответа OCR: наименование позиции, количество, цену за единицу, итоговую сумму по позиции, сумму скидки, сервисный сбор / чаевые, итоговую сумму чека (`total_amount`), дату чека (`tx_date`) и валюту (`tx_currency`).
* **FR-2.4.** Позиции, для которых OCR-сервис вернул коэффициент уверенности `confidence < 0.85`, должны помечаться флагом `needs_review = true` и подсвечиваться в интерфейсе для ручной проверки.
* **FR-2.5.** Система должна выполнять контрольную сверку: сумма всех распознанных позиций с учетом скидок и сборов должна равняться `total_amount`. При расхождении создается техническая позиция «Нераспределенный остаток» на сумму разницы.

### FR-3. Распределение позиций, налоги и алгоритм округления
* **FR-3.1.** Каждая позиция чека может быть распределена между выбранными потребителями (`consumers`) четырьмя способами:
  1. Поровну (`EQUAL`).
  2. В точных суммах (`EXACT`).
  3. В долях / коэффициентах (`SHARES`, например 1:2:1).
  4. В процентах (`PERCENT`, сумма процентов должна строго равняться `100%`).
* **FR-3.2. Распределение скидок и сервисных сборов (чаевых):**
  * Общая скидка по чеку или чаевые распределяются между участниками не поровну, а **пропорционально сумме их индивидуального потребления** в данном чеке.
  * Формула расчета доли участника в чаевых:
    ```text
    Tip_i = Tip_total * (Sum_i / Sum_total)
    ```
    где `Sum_i` — сумма позиций участника `i`, а `Sum_total` — общая сумма позиций в чеке до начисления чаевых.
* **FR-3.3. Правило округления (Алгоритм крупнейшего остатка / Method of Largest Remainder):**
  * Все внутренние вычисления производятся в минорных единицах валюты (копейках, центах) с использованием типа данных с фиксированной точкой (`Decimal` / `NUMERIC(19, 4)`). Использование типов с плавающей точкой (`float`, `double`) запрещено.
  * При делении суммы `S` (в минорных единицах) на `N` долей вычисляется целая часть каждой доли `B_i = floor(D_i)` и неделимый остаток `R = S - sum(B_i)` (где `0 <= R < N`).
  * Остаток `R` распределяется по `1` минорной единице между `R` участниками в порядке убывания дробной части их точной доли `D_i`.
  * **Правило разрешения ничьих (Tie-breaking):** при равенстве дробных частей копейки распределяются в порядке добавления участников в чек, причем сам плательщик (`payer`) получает лишнюю копейку в последнюю очередь.
  * **Инвариант:** сумма округленных долей всех участников по позиции строго равна исходной стоимости позиции `S`.

### FR-4. Мультивалютность и конвертация курсов
* **FR-4.1.** Если валюта траты `tx_currency` отличается от базовой валюты поездки `base_currency`, система выполняет конвертацию в базовую валюту по курсу на дату совершения траты `tx_date`.
* **FR-4.2.** Источником курсов выступает API ЦБ РФ (или ЕЦБ для европейских базовых валют).
* **FR-4.3. Обработка выходных и праздничных дней:** если на дату `tx_date` официальный курс не установлен, система выполняет поиск последнего доступного курса на дату `D <= tx_date` с глубиной поиска до `7` календарных дней.
* **FR-4.4.** Пользователь имеет право вручную изменить курс конвертации для конкретной траты (например, по фактическому курсу списания с банковской карты). При этом фиксируется атрибут `is_custom_rate = true`, а автоматическое обновление курса для этой траты блокируется.
* **FR-4.5.** Конвертация суммы траты в базовую валюту выполняется **до** распределения копеек между участниками, чтобы исключить накопление погрешности при множественном округлении.

### FR-5. Расчет итогового баланса и оптимизация графа долгов
* **FR-5.1.** Для каждого участника `i` вычисляется чистый баланс в базовой валюте поездки:
  ```text
  Net_i = Paid_i - Consumed_i
  ```
  где `Paid_i` — общая сумма, оплаченная участником `i` за всю поездку, а `Consumed_i` — сумма его долей во всех чеках поездки.
* **FR-5.2.** Контрольный инвариант поездки: сумма чистых балансов всех участников всегда равна нулю (`sum(Net_i) == 0.00`).
* **FR-5.3. Алгоритм минимизации транзакций (Debt Simplification):**
  1. Все участники с нулевым балансом (`Net_i == 0`) исключаются из расчета.
  2. Остальные делятся на два списка: Кредиторы (`Net_i > 0`) и Должники (`Net_j < 0`).
  3. На каждой итерации выбирается кредитор `C_max` с максимальным положительным балансом и должник `D_max` с максимальным по модулю отрицательным балансом.
  4. Создается рекомендация на перевод от `D_max` к `C_max` на сумму `X = min(Net_C_max, abs(Net_D_max))`.
  5. Балансы обновляются: `Net_C_max = Net_C_max - X`, `Net_D_max = Net_D_max + X`. Участник, чей баланс стал равен `0`, удаляется из списка.
  6. Шаги 3–5 повторяются до тех пор, пока оба списка не станут пустыми.

## 3. Нефункциональные требования (NFR)

### NFR-1. Информационная безопасность и защита данных (152-ФЗ / GDPR)
* **NFR-1.1. Обезличивание перед OCR:** перед отправкой изображения чека во внешний OCR-сервис бэкенд должен удалять EXIF-метаданные (геолокацию, модель устройства) и применять маску к зонам, содержащим маскированные номера банковских карт и ФИО держателя карты.
* **NFR-1.2. Безопасное хранение медиафайлов:** оригиналы чеков хранятся в приватном бакете S3-совместимого хранилища с шифрованием на стороне сервера (`SSE-S3 / AES-256`). Доступ к файлам предоставляется только по временным подписанным ссылкам (Presigned URL) со временем жизни (TTL) не более `15 минут`.
* **NFR-1.3. Контроль гостевого доступа:** доступ неавторизованных пользователей («Гостей») осуществляется по токену приглашения (криптографически стойкий UUIDv4 + HMAC-SHA256 подпись). Гость имеет права только на чтение трат конкретной поездки и отметку своих позиций; доступ к настройкам поездки, удалению чеков и платежным реквизитам других участников заблокирован на уровне API (RBAC).

### NFR-2. Производительность и отказоустойчивость
* **NFR-2.1.** Время расчета и возврата оптимизированного графа долгов для поездки, содержащей до `50` участников и `500` трат, не должно превышать `200 мс` (95-й перцентиль).
* **NFR-2.2.** Запросы к API курсов валют должны кэшироваться в Redis с ключом `rate:{base}:{target}:{date}` и TTL = `30 дней` (так как исторические курсы не меняются).
* **NFR-2.3. Деградация при отказе внешних API:** если API курсов валют недоступно (таймаут > `3000 мс` или HTTP 5xx), система использует последний закэшированный курс, помечает трату статусом `PENDING_RATE_SYNC` и ставит фоновую задачу на пересчет с экспоненциальной задержкой (retry policy: 1 мин, 5 мин, 15 мин).

### NFR-3. Целостность данных и конкурентный доступ
* **NFR-3.1.** Все операции по изменению состава позиций чека, долей участников и пересчету балансов должны выполняться в рамках единой ACID-транзакции БД.
* **NFR-3.2.** Для предотвращения потери данных при одновременном редактировании одного чека двумя пользователями (Lost Update) применяется механизм оптимистичной блокировки (`Optimistic Locking`) через поле версии записи `version` (`INTEGER`). При несовпадении версий API возвращает код `HTTP 409 Conflict` с актуальным состоянием чека.
