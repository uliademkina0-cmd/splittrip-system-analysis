## Эпик 1: Расчетное ядро и алгоритмы распределения (Core Math Engine)

### US-101: Распределение позиций чека с точным округлением копеек
* **Приоритет:** High (Blocker)
* **Связанные требования:** FR-3.1, FR-3.3, NFR-3.1
* **User Story:**  
  **Как** Участник поездки,  
  **Я хочу**, чтобы система автоматически распределяла неделимые копейки при делении позиции на нескольких человек,  
  **Чтобы** итоговая сумма долгов всех участников всегда до копейки совпадала с суммой оплаченного чека.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Деление суммы с остатком на 3 участников**
  * **Дано:** В чеке есть позиция стоимостью `100.00 RUB`, оплаченная Алисой. В качестве потребителей выбраны `3` участника: Алиса, Боб и Чарли (в указанном порядке).
  * **Когда:** Система сохраняет распределение позиции способом «Поровну» (`EQUAL`).
  * **Тогда:** Боб получает долю `33.34 RUB`, Чарли получает долю `33.33 RUB`, а плательщик Алиса получает долю `33.33 RUB` (согласно правилу Tie-breaking: плательщик получает лишнюю копейку в последнюю очередь).
  * **И:** Сумма всех долей (`33.34 + 33.33 + 33.33`) строго равна `100.00 RUB`.

* **Сценарий 2: Пересчет при изменении состава потребителей**
  * **Дано:** Позиция `100.00 RUB` ранее была разделена на 3 человек.
  * **Когда:** Пользователь удаляет Чарли из списка потребителей этой позиции и сохраняет чек.
  * **Тогда:** Система пересчитывает доли с нуля; Алиса и Боб получают по `50.00 RUB` без накопления предыдущей погрешности округления.

**Технические заметки для разработки:**
* На бэкенде запрещено использовать типы `float` / `double`. Использовать `Decimal` (Python) / `BigDecimal` (Java) / `NUMERIC(19, 4)` (PostgreSQL).

### US-102: Пропорциональное распределение скидок и чаевых
* **Приоритет:** High
* **Связанные требования:** FR-3.2
* **User Story:**  
  **Как** Участник поездки,  
  **Я хочу**, чтобы общие чаевые или скидка по чеку распределялись пропорционально стоимости моего заказа,  
  **Чтобы** не переплачивать за чужие дорогие блюда при равном делении сборов.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Начисление чаевых при разной стоимости заказов**
  * **Дано:** В чеке на сумму `1500.00 RUB` позиция Алисы стоит `1000.00 RUB`, а позиция Боба — `500.00 RUB`.
  * **Когда:** Пользователь добавляет к чеку чаевые в размере `10%` (`150.00 RUB`).
  * **Тогда:** Система распределяет чаевые в пропорции `2:1`: к доле Алисы добавляется `100.00 RUB`, к доле Боба — `50.00 RUB`.
  * **И:** Итоговая доля Алисы составляет `1100.00 RUB`, Боба — `550.00 RUB`.

### US-103: Оптимизация графа долгов (Debt Simplification)
* **Приоритет:** High
* **Связанные требования:** FR-5.1, FR-5.2, FR-5.3, NFR-2.1
* **User Story:**  
  **Как** Участник поездки,  
  **Я хочу** видеть минимальное количество итоговых переводов вместо списка долгов по каждому отдельному чеку,  
  **Чтобы** совершить один банковский перевод вместо десяти.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Схлопывание транзитивной цепочки долгов**
  * **Дано:** В поездке 3 участника (Алиса, Боб, Чарли). По итогам трат Боб должен Алисе `500.00 RUB`, а Чарли должен Бобу `500.00 RUB`.
  * **Когда:** Пользователь открывает вкладку «Итоги взаиморасчетов».
  * **Тогда:** Система отображает ровно `1` рекомендацию по переводу: **Чарли переводит Алисе `500.00 RUB`**.
  * **И:** Сумма чистых балансов всех участников поездки равна `0.00 RUB`.

## Эпик 2: Мультивалютность и интеграция с внешними API

### US-201: Конвертация траты по историческому курсу с обработкой выходных дней
* **Приоритет:** High
* **Связанные требования:** FR-4.1, FR-4.2, FR-4.3, FR-4.5, NFR-2.2
* **User Story:**  
  **Как** Организатор поездки в базовой валюте `RUB`,  
  **Я хочу** вносить траты в иностранной валюте с автоматическим подбором курса на дату чека,  
  **Чтобы** не искать архивные курсы валют вручную.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Трата совершена в выходной день**
  * **Дано:** Базовая валюта поездки — `RUB`. Пользователь создает трату `100.00 EUR` с датой чека `2026-11-15` (воскресенье).
  * **Когда:** Система запрашивает курс `EUR -> RUB` у внешнего API ЦБ РФ.
  * **Тогда:** Поскольку на воскресенье курс не установлен, система находит и применяет курс за последний доступный рабочий день (субботу `2026-11-14`).
  * **И:** В карточке траты отображается курс, фактическая дата курса (`2026-11-14`) и сконвертированная сумма в `RUB`.

* **Сценарий 2: Ручное переопределение курса**
  * **Дано:** Для траты в `EUR` система подтянула официальный курс ЦБ `102.50 RUB`.
  * **Когда:** Пользователь нажимает «Изменить курс», вводит фактический курс списания по карте `105.00` и сохраняет трату.
  * **Тогда:** Система пересчитывает сумму траты и доли всех участников по курсу `105.00`, выставляет флаг `is_custom_rate = true` и отображает метку «Курс указан вручную».

### US-202: Асинхронное распознавание чека через OCR API
* **Приоритет:** Medium
* **Связанные требования:** FR-2.1, FR-2.2, FR-2.3, FR-2.4, FR-2.5, NFR-1.1
* **User Story:**  
  **Как** Участник поездки,  
  **Я хочу** загрузить фотографию длинного ресторанного чека,  
  **Чтобы** не вбивать 20 позиций вручную.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Успешное распознавание с подсветкой сомнительных строк**
  * **Дано:** Пользователь загружает фото чека в формате `JPEG` размером `3.5 МБ`.
  * **Когда:** Внешний OCR-сервис возвращает JSON, где 9 позиций имеют `confidence >= 0.85`, а 1 позиция имеет `confidence = 0.62`.
  * **Тогда:** Чек переходит в статус `PARSED`, 9 позиций отображаются в обычном режиме, а строка с `confidence = 0.62` подсвечивается желтым маркером с подсказкой «Проверьте сумму».

* **Сценарий 2: Расхождение суммы позиций и итога чека**
  * **Дано:** OCR распознал позиции на общую сумму `2850.00 RUB`, но в поле `total_amount` распознано `3000.00 RUB`.
  * **Когда:** Система формирует предпросмотр чека.
  * **Тогда:** В список автоматически добавляется техническая позиция «Нераспределенный остаток» на сумму `150.00 RUB`, чтобы пользователь мог дозаполнить пропущенную строку.

## Эпик 3: Управление участниками и гостевой доступ

### US-301: Фиксация даты выбытия участника из поездки (Mid-trip exit)
* **Приоритет:** Medium
* **Связанные требования:** FR-1.3, FR-1.4
* **User Story:**  
  **Как** Организатор поездки,  
  **Я хочу** указать дату отъезда друга, уехавшего домой раньше остальных,  
  **Чтобы** новые общие траты (бензин, жилье) автоматически делились только на оставшихся участников.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Автоматическое исключение выбывшего участника из новых чеков**
  * **Дано:** В поездке 4 участника (Алиса, Боб, Чарли, Дэйв). Организатор устанавливает для Дэйва дату выбытия `left_at = 2026-11-10`.
  * **Когда:** Создается новая трата «Аренда апартаментов» с датой чека `2026-11-11` и выбирается кнопка «Разделить на всех».
  * **Тогда:** Система включает в список потребителей только `3` человек (Алису, Боба и Чарли); Дэйв в список не попадает.
  * **И:** Все траты Дэйва за даты до `2026-11-10` включительно остаются без изменений в его итоговом балансе.

### US-302: Отметка позиций в чеке Гостем без регистрации
* **Приоритет:** Medium
* **Связанные требования:** NFR-1.3
* **User Story:**  
  **Как** Гость поездки, не желающий регистрироваться в сервисе,  
  **Я хочу** перейти по ссылке от организатора и отметить блюда, которые я ел,  
  **Чтобы** узнать сумму своего долга.

**Критерии приемки (Acceptance Criteria):**
* **Сценарий 1: Доступ по валидной HMAC-ссылке**
  * **Дано:** Организатор скопировал ссылку-приглашение с валидной подписью и отправил ее Гостю.
  * **Когда:** Гость открывает ссылку в браузере, выбирает свое имя из списка участников поездки и ставит галочки напротив двух позиций в чеке за ужин.
  * **Тогда:** Система сохраняет его выбор, пересчитывает доли по этим позициям и отображает Гостю сумму его итогового долга.
  * **И:** Кнопки «Удалить чек», «Изменить курс» и «Настройки поездки» скрыты в интерфейсе и заблокированы на уровне API (`HTTP 403 Forbidden`).
